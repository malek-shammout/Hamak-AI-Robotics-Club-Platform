## 2. Decisions taken

### D-11 — Privileged domain logic lives in the database, not in Server Actions
Every state transition that a user must not be able to choose for themselves
(`submit_application`, `respond_to_offer`, `run_seat_allocation`, `submit_test_attempt`,
`grade_attempt_answer`, `mark_enrollment_completed`, …) is a `SECURITY DEFINER` Postgres
function. Server Actions are thin forwarders that pass parameters and translate errors.

**Reasoning.** These transitions must write tables the caller cannot write directly
(`application_status_history`, `enrollments`, scoring columns). Doing that from the
application layer would require a service-role client in request-handling code — one
mistake away from bypassing RLS everywhere. Putting it in the database keeps the elevated
surface small, enumerable, and testable in a single rolled-back transaction.

**Corollary, and it is not optional:** `SECURITY DEFINER` **bypasses RLS**, so every one of
these functions asserts its own authorisation as its first act — ownership against
`auth.uid()`, or a permission via `app.has_perm()`. That assertion *is* the security
boundary. A function added later without one is a hole, not a style deviation.

### D-12 — BR-05's evaluation half is an A2 attestation; there is no evaluations entity
**Reasoning.** Both frozen documents agree and I checked rather than assumed:
Step 1 §3 says evaluations are "**marked passed by A2**"; Step 2 §B.1 lists the enforcement
layer as "**Domain service**", not a table. The 78-entity inventory has no course-evaluation
entity — M4's assessment tables bind to `applications` (admission screening), not
`enrollments`. So the two halves of BR-05 differ in nature: **attendance is computed and
enforced**, **evaluations are attested**. `mark_enrollment_completed` takes an explicit
boolean the caller must affirm; passing `false` fails the rule exactly as short attendance
does. **Do not add an evaluations table without a recorded D- decision** — that is inventing
schema.

### D-13 — Row scoping is not column scoping
Where a table holds columns the row-owner must not write (scoring, identity, contact
details), row-level policies are **not sufficient**. Such tables get either a column-level
`GRANT` or an RPC-only write path.

**Reasoning.** Learned the hard way, twice — see §4.1 and §4.2. A `FOR ALL` policy that
correctly scopes *which rows* a student may touch says nothing about *which columns*, and
`attempt_answers` holds `awarded_score`.

### D-14 — Lock order is cohort → application, always
**Reasoning.** `respond_to_offer` originally locked application → cohort while the seat
allocator locks cohort → applications. That inversion deadlocks under concurrent load —
two students accepting while A2 runs allocation. Fixed by reordering `respond_to_offer`
(unlocked peek to learn the cohort, then lock cohort, then lock application). Any future
function touching both tables must follow this order.

### D-15 — A question used by a live test is frozen; changes go through versioning
**Reasoning.** Nothing stopped A2 editing a question — or flipping which option is correct —
while a test using it was `ACTIVE`. That silently rewrites a live exam and retroactively
invalidates graded attempts. A trigger now refuses; `clone_question_as_new_version()` is the
sanctioned route, which is what the version chain on `questions` was designed for.

## 3. Design points worth remembering

- **BR-04 is enforced twice, deliberately.** Lazily inside `respond_to_offer` (a missed cron
  run can never let a stale offer be accepted) *and* on a 15-minute schedule (so seats
  actually free up and the waitlist moves even if nobody opens the page). Neither alone is
  sufficient — the lazy check never promotes anyone; the job can lag by one interval.
- **Compute readiness BEFORE allocating.** BR-03 ranks on the *stored* `readiness_score`;
  allocating first ranks on whatever the previous run left behind. The staff UI says so.
- **Only `HELD` sessions count** toward attendance. A cancelled session must never penalise
  a student. `PRESENT` / `LATE` / `EXCUSED` all count as attended.
- **`AttemptCountdown` is display-only.** The deadline is set and enforced server-side; a
  clock-skewed or tampered client still gets refused.
- **`auto_gradable` is derived from question type, never taken from the form.** A
  `SHORT_ANSWER` marked auto-gradable would score 0 forever, silently.
- **`certificates` bucket has no storage policy on purpose.** With RLS on `storage.objects`,
  the absence *is* the enforcement (RR-4). Do not "helpfully" add one.

## 4. Security flaws found — each proven, then fixed, then re-proven

### 4.1 🔴 Student self-grading (migration 0013) — the serious one
`self_answer_test` on `attempt_answers` was `FOR ALL`. It scoped **rows** to the student's
own in-progress attempt but placed **no restriction on columns** — and the scoring columns
live in that table.

> **Proven:** a student `UPDATE`d their own `awarded_score` to **999.00** and it persisted.

Because BR-02 gates admission on that score, this was a direct route to fraudulent
admission. **Fixed:** students hold `SELECT` only; all writes go through
`save_attempt_answer()`, which touches no scoring column. Re-running the identical attack
now fails.

### 4.2 Contributor names unreachable → the tempting wrong fix (migration 0007)
Public project pages rendered team members as "Not available": `users` has no anon policy,
correctly. The tempting fix — `using (true)` on `users` — would have published every
member's email, phone and account status. **Fixed with two independent locks:** a row policy
limiting anon to people credited on *published* content, **plus** a column-level grant of
`(id, full_name_ar, full_name_en)` only. Verified as `anon`: name readable, `select email`
refused with `42501`.

### 4.3 Child tables of published parents were invisible (migration 0006)
`schema.sql` opened the published *parents* but not their children. A published project
would have rendered with **no technologies, no team, no media** — silently. Children now
inherit the parent's `publication_status`. `project_bom_lines` deliberately excluded: a bill
of materials exposes hardware holdings and unit costs.

### 4.4 Live exam mutable (migration 0015)
See D-15.

### Also fixed
- **Mutable `search_path`** on 8 `app`-schema trigger functions (advisor lint 0011). I had
  pinned it on the SECURITY DEFINER helpers and missed the triggers — exactly the
  inconsistency the linter exists to catch. Advisor now reports 0 such warnings.
- **`system_policies` unreadable by anon** (migration 0004): `club.location` returned zero
  rows and `ClubMap` rendered nothing. Fixed with an explicit **key allow-list**, not
  `using (true)`; operational keys (SLA, loan horizon) remain staff-only.

   policies *before* writing code. `checkouts`, `checkout_lines`, `liability_records` hold
   columns a student must not write — apply D-13 deliberately.

   `check_in_line` (BR-06 — Damaged/Lost opens a liability; `CK_RETURN_INSPECTED`),
   `resolve_liability` (A7-only waiver per `CK_LIABILITY_WAIVER_ACTOR`).
3. **Verify adversarially**: BR-07 (one active checkout per serialized unit),
   `CK_LINE_SERIALIZATION`, BR-12 context exclusivity, BR-13 cross-cohort custody block,
   RR-3 (consumables excluded from the return obligation).
4. **A3 UI**: asset catalogue, issue/return desk, liability queue.
5. **Then M6** — clearance evaluation against C1–C5 and certificate issuance, which is
   finally buildable once M5 exists.

**Recommended before any of that:** commit the probes as a real test suite (item 1). They
already exist as SQL; making them repeatable is cheap and turns a one-off check into a
regression net.
