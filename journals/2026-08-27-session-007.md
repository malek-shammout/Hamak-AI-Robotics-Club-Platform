## 2. Decisions taken

### D-22 — publishing is gated on `<module>.APPROVE`, never on `UPDATE`
`staff_update` on the five publishable entities carried no column restriction, so anyone who
could EDIT a row could flip `publication_status` and put it on the public site.

**Proven, not suspected.** A user granted `M7.READ/CREATE/UPDATE` and explicitly *not*
`M7.APPROVE` published a project. The only thing that briefly stopped it was
`ck_project_published_stamped` — a data-integrity check, not an authorisation gate — and
supplying `published_at` by hand satisfied it. The other four entities have no such check at all.

**Why it was invisible.** In the seed, every role holding UPDATE for a module also holds APPROVE
for it. The distinction had never been exercised. It becomes exploitable the moment a drafting
role exists — a junior member writes, a lead publishes — which is precisely what an authoring UI
invites. The permission model already drew the line; nothing enforced it.

**Why a trigger and not a column grant.** This is D-13's shape for a fifth time, but its usual
remedies do not fit: publication is a **transition**, comparing OLD to NEW, and a column
privilege cannot see that. `app.assert_publish_authorised()` can. It also stamps `published_at`
server-side — a bogus client value of `2001-01-01` was proven overridden — because a timestamp
the caller dictates is not evidence of anything.

The guard is deliberately narrow: moving *to* `DRAFT` or `PENDING_REVIEW` needs no approval, or a
drafter could not withdraw their own mistake and would have to ask someone else, which makes the
audit trail worse rather than better.

*Migration 0025, test 13.*

### The one that looked like a product bug and was not
The first signed-in run failed 3 session specs: sign in, navigate, reload → bounced to `/login`.
That reads as "sessions do not survive a refresh", which would be a serious defect.

The server log said otherwise:

```
POST /en/login → signIn ✓ → GET /en/me/applications 200   ← the session worked
POST /en/courses → signOut                                 ← a concurrent sign-out
GET  /en/me/applications 307 → /en/login                   ← only now the bounce
```

`supabase.auth.signOut()` takes no scope argument, so it defaults to **`scope: 'global'`** and
revokes *every* session for that user. With `fullyParallel: true` and one shared account, the
sign-out spec was killing the sessions of the reload and language-switch specs mid-flight.

Proven rather than argued: **5/5 pass on one worker, 3/5 in parallel.**

The fix belongs in the runner, not the assertions, and the reason is written into
`e2e/auth/fixtures.ts` — where the next person to see a red session spec will actually read it —
with an explicit warning not to relax the assertions instead of checking the worker count.

**The scope default is a product question, not a defect.** Nobody chose global; it is what
Supabase does when passed nothing. It is defensible on shared lab machines and surprising
everywhere else, so it is recorded for the club rather than changed unilaterally.

### The lint fix immediately earned itself
Within minutes of working, `react-hooks/static-components` flagged code written the same hour:
`PublishControls` defined `TransitionButton` inside its own body, making it a new component type
on every render — React would unmount and remount the form, losing the pending state of an
in-flight submit. Not something typecheck or a test would have caught.

### The gap I could not close
The provisioned test account holds **0 roles**. So the staff specs assert "renders or redirects
cleanly" — they do **not** verify what an authorised staff member actually sees, and the
authoring UI I built today has never been driven with real staff permissions.

I could have granted that account a role to see the screens. I did not: changing a person's
authorisation on the club's live system is not mine to do unasked, and a test account quietly
holding staff rights is exactly the kind of thing that is forgotten and later exploited.

**Known flake:** one sign-out spec failed once in the first full serial run and passed in two
subsequent full runs. Most plausible cause is ~50 real sign-ins in 4 minutes brushing Supabase's
auth rate limit. Not reproduced; recorded rather than papered over. The proper fix is Playwright
`storageState` — sign in once, reuse — which also removes most of the 4.4-minute runtime.
