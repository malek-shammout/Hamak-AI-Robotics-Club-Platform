## Decisions taken this session

### D-09 — BR-01 enforced declaratively (closes RR-2)
RR-2 flagged that a plain FK cannot verify the *state* of the referenced clearance row, and
proposed "trigger or composite FK". **Chose the composite FK.**

`clearance_records` gained `UNIQUE (id, status)`. `certificates` carries a mirrored
`clearance_status` column with:

```sql
foreign key (clearance_record_id, clearance_status)
  references clearance_records (id, status) on update restrict
check (clearance_status in ('APPROVED','APPROVED_BY_OVERRIDE'))
```

Two properties fall out of this, both wanted:
1. A certificate cannot be inserted against a non-approved clearance.
2. A clearance cannot be moved *out* of an approved state while a certificate references it —
   `on update restrict` blocks it.

BR-01 now holds at the storage layer with no trigger and no application code. The mirrored
column is a controlled denormalisation whose only purpose is to carry the constraint; it is
not free-form data and must never be written independently.

### D-10 — Supabase Auth owns credentials
The ERD's `users.password_hash` is incompatible with Supabase Auth. Dropped it;
`public.users.id` is now `references auth.users(id)`. `token_epoch` was kept — still useful
for invalidating live JWTs on a role change.

### RR-3 — confirmed by the club
Consumables (`asset_types.is_consumable = true`) are **excluded** from the BR-01 return
obligation. Rather than scatter that filter across the codebase, it lives in one view:
`v_enrollment_outstanding_items`. The clearance evaluator reads only that view.

## Bug found and fixed during review

The Reviewer pass caught an ordering fault: the seed `INSERT`s were placed **after**
`alter table … force row level security`. With `FORCE` on and every policy scoped
`to authenticated` / `to anon`, the migration role would have been denied and the entire
seed would have failed. Sections were reordered — seed now runs before RLS enforcement.
