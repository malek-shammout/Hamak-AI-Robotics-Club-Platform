## 1. What shipped

### Database test suite — the foundation
`supabase/tests/` (8 files) + `scripts/run-db-tests.mjs`, wired into `npm run test:db`
and `npm run verify`.

Each test is a self-contained adversarial probe that ends with
`raise exception 'ALL_..._PASSED'`. That raise **aborts the transaction**, so a test never
persists a row — pass or fail. The runner treats that message as success and everything
else as failure, **including a test that returns cleanly**, which would mean its closing
assertion never ran.

## 2. Decisions taken

### D-16 — Every business rule ships with a committed adversarial test
A rule verified once by an ad-hoc probe is not verified; it is *anecdote*. Rules now live
in `supabase/tests/` and run on every `npm run verify`.

**Reasoning.** Session 002 proved seven rules with hand-written probes that were then
thrown away. Nothing would have caught a regression. The suite justified itself twice
within hours of existing — see §4.

**Constraint that makes it safe:** a test must end in `raise exception 'ALL_..._PASSED'`
so the transaction aborts. A test that commits rows is a broken test, and the runner
treats a clean return as a failure precisely to catch that.

### D-17 — Custody and liability tables are RPC-write-only
`checkouts`, `checkout_lines` and `liability_records` have **no staff write policies**.
Every mutation goes through `issue_checkout`, `check_in_line` or `resolve_liability`.

**Reasoning.** These carry BR-06, BR-07, BR-12 and BR-13, and a liability is a financial
and legal record. A hand-edit that skips `resolve_liability()` skips BR-06 with it —
which is exactly what was proven possible before this change. Catalogue tables
(`asset_types`, `asset_units`, `storage_locations`, `bulk_stock`, `kit_*`) keep ordinary
staff CRUD, because that is inventory bookkeeping, not custody state.

**Verifiable consequence:** the live policy count fell from 380 to **371** — precisely the
nine policies dropped.

## 3. 🔴 The gap: BR-06's A7-only waiver was enforced nowhere

Auditing M5's RLS *before* writing code — as the plan required — produced one reassuring
result and one alarming one.

**Reassuring:** zero `FOR ALL` non-admin policies across all 14 M5 tables. The
`attempt_answers` class of flaw from Session 002 does not exist here.

**Alarming:** `ck_liability_waiver_actor` reads

```sql
CHECK (status <> 'RESOLVED_WAIVED' OR (waived_by IS NOT NULL AND waiver_justification IS NOT NULL))
```

It requires only that *someone* is named. A CHECK cannot see roles — yet claude.md §4
documents this constraint as enforcing "BR-06, **A7-only** waiver", and `staff_update`
granted UPDATE to anyone holding `M5.UPDATE`, i.e. the whole Logistics team.

> **Proven against the live database:** a LOGISTICS member set
> `status='RESOLVED_WAIVED', waived_by=<self>` on a 250 SYP liability, and it persisted.

This is **D-13 for the third time**: a row policy restricts which ROWS you may touch,
never which COLUMNS or VALUES. Three separate flaws, one root cause:

| Session | Table | What leaked |
|---|---|---|
| 002 | `attempt_answers` | a student self-graded to 999.00 |
| 002 | `users` | needed column grants to credit contributors safely |
| 003 | `liability_records` | a non-admin waived a financial liability |

**Fixed** by D-17 plus an explicit `app.is_admin()` assertion inside `resolve_liability`.
Test 07 now attacks it two ways — a direct `UPDATE` as `authenticated`, and the RPC as a
Logistics member — and both are refused.

## 4. The suite earning its keep, twice, on day one

**First run:** test 01 failed. It was written before migration 0002 added the
`auth.users → public.users` bridge and still inserted the profile row by hand, colliding
on `users_pkey`. Exactly the drift a suite exists to catch — and proof the suite *can*
fail, which a green-only suite never demonstrates.

**Signature change:** reordering `issue_checkout`'s parameters broke test 07 instantly.
Rewritten to **named notation**, which is what a regression test should use — it is immune
to future reordering.

## 6. Design points worth remembering

- **A1 must never enter the BR-01 conjunction.** It is returned with `blocking:false`,
  shown to A3/A7 only, and omitted entirely from the student projection. §B.2 says it is
  "not shown to student"; it concerns *other* enrolments. Test 08 fails if this changes.
- **RR-3 lives in exactly one place.** C2 and C3 read `v_enrollment_outstanding_items`.
  Do not re-implement the `is_consumable` filter anywhere else.
- **`issue_certificate` writes `clearance_status` from the LOCKED clearance row**, never a
  parameter — so the D-09 composite FK cannot be circumvented even by that function.
- **`approve_clearance` always re-evaluates** before deciding. Approving on a snapshot
  that went stale between page load and click is how an uninspected return slips through.
- **UI hiding is courtesy, never enforcement.** The waiver option is admin-only in the
  form *and* refused by the database with `WAIVER_REQUIRES_ADMIN`.
